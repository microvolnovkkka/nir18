## 3. Основной запуск через Docker

Из корня клонированного проекта:

```sh
./scripts/init-env.sh
docker compose config --quiet
docker compose up -d --build
docker compose ps -a
./scripts/check-local.sh
```

`init-env.sh` не перезаписывает существующий `.env`, создаёт файл с доступом только владельцу и случайным hex-паролем через openssl. Не выводит пароль. Windows: Git Bash + openssl либо вручную скопировать пример и задать случайный hex-пароль. Требование hex упрощает безопасное включение пароля в DATABASE_URL; произвольные символы требуют URL-encoding, которого шаблон Compose не выполняет.

Первая сборка скачивает образы и зависимости. PostgreSQL не публикует порт на хост; API доступен только внутри Docker-сети; с хоста открыт `127.0.0.1:8080`. Caddy раздаёт React и проксирует `/api`/`/media`. При занятом порте изменить WEB_PORT и APP_ORIGIN в .env, затем повторить up. Для другого порта `./scripts/check-local.sh http://localhost:8090`.

Ожидаемая готовность:

```text
GET /api/health/live  → 200 {"status":"ok"}
GET /api/health/ready → 200 {"database":"ok","schema":"ok","status":"ready"}
```

Если БД недоступна/схема отсутствует, ready → 503. migrate Exited(0) — нормальная работа одноразового контейнера. Фронтенд не выдаёт эту проверку за готовность входа/публикаций. `GET /api/publications` сейчас 404.

Просмотр журнала без содержимого .env:

```sh
docker compose logs --tail=100 api migrate db web
```

Остановка: `docker compose stop` или `docker compose down`; повторный запуск — `docker compose up -d`. `down -v` удаляет БД и медиа и не нужен для обычного обновления. Не удаляйте тома ради исправления миграции. Изменение пароля в .env не меняет пароль существующего PostgreSQL-тома автоматически.

## 4. Миграции и начальные данные

Runner встраивает SQL в бинарник. Запускает файлы по номеру, сверяет SHA-256 применённых файлов, держит advisory lock на соединении, каждый файл выполняет в отдельной транзакции. Успех записывает в schema_migrations. Повтор не создаёт дубли. При ошибке файл откатывается; запуск исправленной **неприменённой** миграции допустим. Применённые SQL менять нельзя. Автоматических down/rollback-миграций нет; исправление — следующая forward-миграция либо восстановление согласованной копии.

После новой миграции обновить `LatestVersion` в migrations.go и проектную схему. Сначала проверить на отдельной БД. Применение к текущей локальной БД при обновлении:

```sh
docker compose stop web api
docker compose build api migrate
docker compose run --rm migrate
docker compose up -d
```

При ошибке migrate не продолжать запуск приложения до исправления. Для первоначального запуска порядок уже встроен в depends_on. Проверка истории:

```sh
docker compose exec db psql -U nir -d nir -c 'SELECT version,name,applied_at FROM schema_migrations ORDER BY version;'
```

В командах psql выше default nir; при смене POSTGRES_USER/DB используйте свои значения. В scripts/check-local.sh они берутся из контейнера автоматически.

Сиды: пять участников с фиксированными UUID, пять направлений и 15 исходных подтем из PROJECT_CONTEXT §5. Ни опубликованных образцов, ни реальных паролей. Аккаунты **неактивны**. Служебную CLI настройки паролей, вход и права реализуем в части 2. Создание записей не означает, что авторизация работает.

## 5. Разработка без пересборки фронтенда

Для обычной проверки достаточно Docker; локальные Go/Node не обязательны. Для разработки установить Node 24 и pnpm 11.25.0, Go ≥1.26.1 из официальных источников. Сборка локально:

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm build
cd ../backend
go test ./...
go vet ./...
go build ./cmd/api ./cmd/migrate
```

В текущей Codex-среде `node` не был в PATH, поэтому первая локальная команда pnpm build остановилась на `node: not found`; после добавления предоставленного Node в PATH сборка прошла. Docker-сборка от этой настройки хоста не зависит. Не копируйте машинные пути Codex другим участникам как обязательную установку.

Для Vite dev proxy ожидает Go на 127.0.0.1:8081. При желании запускать Go на хосте поднимите **отдельный локальный** PostgreSQL или явный Compose override с портом только loopback, задайте DATABASE_URL (sslmode=disable только для локального стенда), затем `go run ./cmd/migrate` и `go run ./cmd/api`. `pnpm dev` — в другом терминале. По умолчанию Compose API-порт на хост не открыт; `pnpm dev` без отдельного API ожидаемо покажет ошибку. Это необязательный вариант, основной проверенный путь — Compose.

## 6. Файлы, заглушка и ограничения

PostgreSQL 18 хранит данные в томе `/var/lib/postgresql` (версионный PGDATA внутри), media_data примонтирован к `/var/lib/nir/media`, Go работает uid 10001. Проверено, что пользователь контейнера может записывать в этот том. Загрузчик/выдача/очиститель пока не реализованы; тестовый файл проверяет сохранность тома, а не работу изображений приложения.

`internal/bot.Stub` проверяется напрямую: сохраняет исходный Markdown, возвращает заметное предупреждение, уважает ctx, допускает управляемую задержку и типизированную ошибку. HTTP `/api/bot/respond` не включён до middleware входа/прав. BOT_MODE/APP_ORIGIN/COOKIE_SECURE в Compose зарезервированы для следующих карточек; сейчас сервер их не использует. Никакой внешней генерации и ключей нет.

Резервное копирование/восстановление спроектировано в архитектуре, но полный backup/restore с публикациями и файлами здесь не выполнен. Продакшен, HTTPS, отдельная роль БД, обработчики медиа и пользовательская приёмка относятся к будущим этапам.
