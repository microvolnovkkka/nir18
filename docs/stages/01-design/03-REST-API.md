# 03. REST API первой версии

**Версия:** v1, 28.10.2026. **Статус:** проект полной первой версии; в части 1 реализованы только технические проверки здоровья. Предметные обработчики относятся к следующим карточкам.

**Кому обязательно прочитать:** Фёдору и Андрею; Александру — общие правила и раздел 8, затем полный контракт бота.
**Какие разделы особенно важны:** права/повторы/даты, операции публикаций и изображений. Content manager использует описание экранов, этот файл — при уточнении ошибок.

## 1. Общие правила

Один origin, `/api` для JSON; изображения `/media/{id}`. Версия v1 пока зафиксирована документом, без `/v1` в URL. Поля JSON — snake_case, UTF-8, запросы `Content-Type: application/json`; исключение — multipart загрузка. Неизвестные поля/параметры и повтор одного query-параметра отклоняются, пустое тело там, где оно требуется, — ошибка. `null` разрешён только там, где явно указан. Одна JSON-величина на тело, без хвостовых данных. Клиент не передаёт автора, дату, права и статус публикации.

ID публикации/файла/автора — UUID canonical lowercase; ID каталога — положительное целое smallint. UUID в примерах иллюстративны, не гарантируют существование записи. Некорректный ID — 400, синтаксически корректный отсутствующий — 404. Ответы JSON `Cache-Control: no-store`; публикации могут получить управляемое кеширование позже. Бинарные ответы также пока `private, no-store`, чтобы удаление/изменение доступности не обходилось публичным кешем.

Авторизация: cookie `nir_session` (HttpOnly, SameSite=Lax, Path=/, 7 суток; Secure=true при HTTPS). Для всех изменяющих запросов проверяется точный `Origin` из конфигурации, запрещён CORS с чужих origin; для вошедшего пользователя дополнительно `X-CSRF-Token` из login/me. Login проверяет Origin, JSON и ограничения попыток без предварительного CSRF. Logout без действующей сессии проверяет Origin и возвращает 204; с действующей — ещё CSRF. Подробности — [архитектура §2](05-Архитектура-и-проверки.md).

### Общая ошибка

```json
{"error":{"code":"validation_failed","message":"Проверьте поля","fields":{"title":"Укажите заголовок"}},"request_id":"d6d15cb5-523c-4d62-897e-59f6178888e0"}
```

`fields` — объект строк (может быть пустым), `request_id` — серверный ID запроса для журнала; секретов/SQL в ответе нет. Для бота корреляция описана в его контракте. На каждом ответе `X-Request-ID`.

| Статус | code | Смысл |
| --- | --- | --- |
| 400 | bad_request | сломанный JSON, тип, ID, query, повтор/неизвестное поле |
| 401 | unauthenticated / invalid_credentials | нужна сессия / неверный вход |
| 403 | forbidden / csrf_failed | чужая статья / неверный Origin или CSRF |
| 404 | not_found | ресурс отсутствует или файл скрыт от этого пользователя |
| 409 | idempotency_conflict / media_unavailable / upload_in_progress | конфликт ключа, файл уже очищается/истёк, загрузка ещё не завершена |
| 412 | stale_publication | If-Match не совпадает с текущим ключом |
| 413 | payload_too_large | превышен размер запроса/файла |
| 415 | unsupported_media_type | неверный Content-Type/формат изображения |
| 422 | validation_failed / invalid_image | корректный JSON, но недопустимые значения / повреждённое изображение |
| 428 | precondition_required | нет If-Match или обязательного Idempotency-Key |
| 429 | rate_limited | превышен лимит; Retry-After в секундах |
| 500 | internal_error | непредвиденная ошибка, без ложного успеха |
| 503 | unavailable / storage_unavailable | БД/диск временно недоступны |

Все операции могут дать 500/503; все изменяющие — 403 по CSRF, 413/415 для тела. Поведение при истечении сессии — 401, текст остаётся в открытой вкладке. В ответах 204 тела нет. GET/HEAD не меняют данные. Неподдерживаемый метод — 405 с Allow.

### Рабочие технические лимиты

Заголовок 1–200 символов, Markdown 1–200 000 символов/800 000 байт; JSON-запрос публикации ≤ 1 МиБ. Пробельные значения не считаются заполненными. Не более 100 уникальных внутренних изображений в статье. Параметры не являются дополнительными условиями исходного ТЗ; меняются совместно в валидаторе, БД и документации. Лимиты бота определены только в его контракте.

## 2. Вход, выход и пользователь

### `POST /api/auth/login`

Доступ всем, path/query нет. Тело:

```json
{"login":"fmavrin","password":"<личный пароль>"}
```

Логин trim/lowercase, 3–32 ASCII (`[a-z][a-z0-9_]*`); пароль не trim, 12–128 Unicode-символов, максимум 512 байт. Сервер сравнивает Argon2id; для неизвестного/неактивного пользователя выполняет эквивалентную проверку и даёт одинаковую ошибку. Рабочий лимит: 5 неудач/15 минут для пары IP+логин, 30/15 минут для IP. Значения конфигурируемы. При успехе новая сессия, старая cookie-сессия этого браузера отзывается; Set-Cookie и 200:

```json
{"user":{"id":"00000000-0000-4000-8000-000000000001","display_name":"Фёдор Маврин","login":"fmavrin"},"csrf_token":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","expires_at":"2026-11-04T09:00:00Z"}
```

Ошибки 400/422, 401 invalid_credentials, 429. При потерянном ответе повтор входа допускается (новая сессия, без публикаций); не выполнять автоматические циклы.

### `GET /api/auth/me`

Нужна сессия; path/query/тело отсутствуют. 200 с тем же объектом user, csrf_token и expires_at, что в login; 401 при отсутствии/истечении. Пароль/хеш не возвращается. Повтор безопасен.

### `POST /api/auth/logout`

Query/тело отсутствуют. При сессии — проверка Origin/CSRF, отзыв в БД; очистка cookie с теми же атрибутами, 204. Без сессии — Origin и 204 с очисткой cookie. Повтор безопасен. Ошибки 403/503; при недоступной БД не заявлять об отзыве существующей сессии.

## 3. Каталог и авторы

### `GET /api/directions`

Публично, без query/тела. 200, полный небольшой список по position:

```json
{"items":[{"id":1,"name":"Распознавание эмоций по лицу — MediaPipe Face и FER-модели","position":1}]}
```

Пример сокращён до одного элемента; фактически возвращаются пять. Ошибки 400 для неизвестного query, 503. Повтор безопасен.

### `GET /api/subtopics?direction_id=1`

Публично, необязательный direction_id. Без него — все подтемы по direction.position, subtopic.position; с ним — относящиеся к направлению. Тела/path нет. 200:

```json
{"items":[{"id":101,"direction_id":1,"name":"Модели представления эмоций в компьютерном зрении.","position":1}]}
```

400 для типа, 422 для несуществующего направления. Пустой действующий справочник — items:[], не 404. Повтор безопасен.

### `GET /api/authors`

Публичный список пяти участников для фильтра, без path/query/тела; логинов и статуса доступа нет. Порядок по display_name, id. 200:

```json
{"items":[{"id":"00000000-0000-4000-8000-000000000001","display_name":"Фёдор Маврин"}]}
```

Пример сокращён; ошибки общие. Это не панель пользователей, изменяющих операций нет.

## 4. Список, поиск, даты и пагинация

### `GET /api/publications`

Публично, тела/path нет. Все фильтры объединяются **AND**.

| Query | Тип / default | Правило |
| --- | --- | --- |
| q | строка, пусто | trim, 0–200 символов; пусто = без поиска |
| direction_id | smallint | существующий ID |
| subtopic_id | smallint | существующий ID; при указанном направлении должен ему принадлежать |
| author_id | UUID | существующий пользователь |
| date_from, date_to | YYYY-MM-DD | календарные даты в Europe/Moscow, границы включены |
| page | int, 1 | 1…10000 |
| page_size | int, 20 | 1…50 |

Пустое значение числового/даты — 400, отсутствие — без ограничения. date_from ≤ date_to, иначе 422. `date_from` превращается в 00:00 этой даты по Москве (включительно); date_to — в 00:00 следующего дня (исключительно). Например, 28.10.2026: `[2026-10-27T21:00:00Z, 2026-10-28T21:00:00Z)`. Сравнение только по updated_at. Сортировка фиксирована `updated_at DESC, id DESC`.

Поиск: одна введённая фраза как буквальная регистронезависимая подстрока `title || '\n' || markdown`, без морфологии, исправления опечаток и внешнего поиска. `%`, `_`, `\` экранируются как литералы; SQL-параметры обязательны. Русский и латинские термины обрабатываются одним правилом, ILIKE с UTF-8 locale. Разметка тоже часть исходного содержимого; это допустимое ограничение первой версии. Индекс pg_trgm ускоряет длинные запросы; короткие допускаются и могут сканировать небольшой каталог.

200:

```json
{"items":[{"id":"10000000-0000-4000-8000-000000000001","title":"Модели эмоций","author":{"id":"00000000-0000-4000-8000-000000000001","display_name":"Фёдор Маврин"},"direction":{"id":1,"name":"Распознавание эмоций по лицу — MediaPipe Face и FER-модели"},"subtopic":{"id":101,"name":"Модели представления эмоций в компьютерном зрении."},"updated_at":"2026-10-28T09:00:00Z"}],"page":1,"page_size":20,"total":1,"total_pages":1}
```

Для пустого списка items:[], total:0, total_pages:0. Страница после конца — 200 с пустыми items и реальными total/total_pages. COUNT и SELECT выполняются в одной read-only REPEATABLE READ транзакции для согласованного ответа. Между двумя запросами список может измениться после обновления статьи; пагинация не является снимком/историей. Ошибки 400, 422 на неверную пару/диапазон/несуществующий фильтр. Повтор безопасен.

## 5. Чтение и изменение статьи

### `GET /api/publications/{id}`

Публично, query/тела нет. 200 + заголовок `ETag: "<revision_key>"`:

```json
{"id":"10000000-0000-4000-8000-000000000001","title":"Модели эмоций","markdown":"## Введение\nТекст отчёта.","author":{"id":"00000000-0000-4000-8000-000000000001","display_name":"Фёдор Маврин"},"direction":{"id":1,"name":"Распознавание эмоций по лицу — MediaPipe Face и FER-модели"},"subtopic":{"id":101,"name":"Модели представления эмоций в компьютерном зрении."},"updated_at":"2026-10-28T09:00:00Z","revision_key":"20000000-0000-4000-8000-000000000001"}
```

Ошибки 400/404. Список media отдельно не требуется: сервер разбирает Markdown, а ссылки ведут на `/media/{id}`. Повтор безопасен.

### Общие правила записи

POST/PUT/DELETE публикаций требуют сессии, CSRF и `Idempotency-Key: <UUID>`. Ключ создаётся браузером при подтверждении и сохраняется вместе с **точным** запросом до определённого результата; при сетевой ошибке повторяется этот же запрос/ключ. Новые правки — новый ключ. Хранение квитанций 7 суток, затем без проверки каталога не повторять. Сервер возвращает исходный короткий ответ с `Idempotency-Replayed: true` при повторе; ошибка/rollback не резервирует ключ. Разный запрос с тем же ключом — 409. Повтор успешного DELETE возвращает 204, даже если статьи уже нет, но только для владельца квитанции. Повтор успешной записи не меняет updated_at.

Сервер определяет автора из сессии. Единственная дата и revision_key меняются на каждой новой успешной записи (даже если текст совпал); часы клиента игнорируются. Направление выводится из subtopic_id. Markdown разбирается библиотекой, внутренние ссылки проверяются по AST, не только regexp. В статье допускаются лишь внутренние изображения владельца, ready, доступные; несуществующие/чужие — 422 media_ids в fields; истёкшие/очищаемые — 409. Разметка/источники не открываются сервером. Сырой HTML отключён в общем рендерере, опасные URL не исполняются.

PUT/DELETE дополнительно требуют `If-Match: "<revision_key>"` (один сильный ETag; `*`, списки и weak запрещены). Проверяется внутри транзакции после автора и обработки повтора. Несовпадение — 412, не перезаписывать автоматически. При потере ответа сначала повторить исходный запрос, затем GET; нельзя подменять If-Match свежим ключом и молча повторять старые правки.

### `POST /api/publications`

Любой вошедший участник, после подтверждения UI. Path/query нет. Тело:

```json
{"title":"Модели эмоций","subtopic_id":101,"markdown":"## Введение\nТекст отчёта."}
```

201, `Location: /api/publications/<id>`, ETag и:

```json
{"id":"10000000-0000-4000-8000-000000000001","revision_key":"20000000-0000-4000-8000-000000000001"}
```

Далее GET для отображения сохранённого материала. Значимые ошибки: 400, 401, 403, 409, 422, 428, 413, 503. Квитанция, текст и связи записываются атомарно. Никакого `draft`, `publish=true`, авторства и даты в теле нет.

### `PUT /api/publications/{id}`

Только автор, полная замена изменяемых полей title/subtopic_id/markdown. Тело такой же формы, что POST; query нет. 200 + новый ETag, короткий объект id/revision_key той же формы. Старое содержимое видно читателям до commit; предыдущий текст не сохраняется. Ошибки общие плюс 403 чужому автору, 404 отсутствующей статье, 412/428 для предусловия. Бот при этом не вызывается.

### `DELETE /api/publications/{id}`

Только автор, после подтверждения UI. Query/тела нет, ключ и If-Match обязательны. 204. Связи снимаются, файлы очищаются отложенно при отсутствии других связей/аренды. Ошибки 401/403/404/409/412/428/503. Повтор без той же квитанции для уже удалённой статьи — 404. Корзины и восстановления API нет.

## 6. Изображения

### `POST /api/media`

Только участник + CSRF/Origin. Query/path нет. `multipart/form-data`, ровно поле `upload_id` (UUID, сгенерированный клиентом) и часть `file` (один файл). Multipart boundary задаёт браузер, вручную Content-Type не собирать. Максимум всего запроса 6 МиБ, файла — 5 МиБ, пикселей — 20 000 000; PNG/JPEG/WebP. Не доверять расширению/MIME клиента, проверить сигнатуру, размеры и полное декодирование с ограниченными ресурсами. Имя очищается до имени файла, 1–255 символов; путь формируется только из UUID и проверенного типа.

201:

```json
{"id":"30000000-0000-4000-8000-000000000001","url":"/media/30000000-0000-4000-8000-000000000001","mime_type":"image/png","byte_size":15234,"width":800,"height":600,"lease_until":"2026-10-29T09:00:00Z"}
```

При потерянном ответе повторить тот же upload_id и байты. Совпали владелец, sha256 и ready — 200 с теми же метаданными; другой файл с тем же ID — 409 idempotency_conflict; чужой ID — 404; staging — 409 upload_in_progress с Retry-After: 2. После окончательно неудачной/истёкшей загрузки клиент создаёт новый upload_id. Ограничение временных файлов: 100 штук/500 МиБ на владельца, настраивается; 429. Это не ограничения числа опубликованных статей. Ошибки 401/403/413/415/422/503. Ответ не сохраняет статью.

### `POST /api/media/lease`

Участник + CSRF. Query/path нет, JSON:

```json
{"ids":["30000000-0000-4000-8000-000000000001"]}
```

1–100 уникальных UUID. Продлить только собственные ready-файлы из текущего редактора до now()+24h; непривязанный файл должен иметь действующую аренду. Для связанного файла допускается продление независимо от старой lease. Проверить/заблокировать все строки, при любой ошибке не обновлять ничего. 200:

```json
{"lease_until":"2026-10-29T09:10:00Z"}
```

Интерфейс вызывает каждые 10 минут при открытом редакторе, при возврате к вкладке и перед сохранением; пустой список не отправляет. При ошибке сохраняет текст и сообщает о проблеме. Повтор безопасен, лишь сдвигает срок. 401, 404 для чужого/неизвестного, 409 для истёкшего/deleting/staging, 422 для списка. Это продление файлов, не автосохранение документа.

### `GET /media/{id}` и `HEAD /media/{id}`

Query/тела нет. Публично, если ready и есть хотя бы одна связь; иначе только владельцу при действующей сессии/lease. Для скрытого/отсутствующего/не-ready файла одинаковый 404; некорректный UUID — 400. 200 с байтами, `Content-Type` из проверенных метаданных, `Content-Length`, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, `Cache-Control: private, no-store`. HEAD — те же заголовки без байтов. Range в первой версии не поддерживается (обычный полный 200); If-None-Match не требуется. Пример результата: бинарный PNG, не JSON/base64. Если запись есть, а файла нет — 503, запись диагностируется, не выдаётся пустое изображение. Повтор безопасен.

Нет ручного DELETE media: автор удаляет вставку из Markdown, сохранение снимает связь, уборка учитывает остальные статьи. Новый файл при замене получает другой URL.

## 7. Технические проверки каркаса

`GET /api/health/live`: публично, без параметров/тела; 200 `{"status":"ok"}` — процесс отвечает.

`GET /api/health/ready`: публично, без параметров/тела; проверка pgx Ping и наличия ожидаемой версии миграций; 200 `{"status":"ready","database":"ok","schema":"ok"}`, иначе 503 `{"status":"not_ready"}`. Подробности подключения не раскрываются. Это технический контракт части 1, исключение из предметной формы ошибок выше. Другие маршруты в каркасе возвращают 404 и не означают реализованные операции.

## 8. Запрос бота

`POST /api/bot/respond` — только участник, Origin/CSRF, JSON, без path/query; синхронный ответ целиком, без SSE и сохранения диалога. **Полные поля, примеры успеха/ошибки, лимиты, отмена и повторы находятся исключительно в [04-Контракт-бота.md](04-Контракт-бота.md).** Это единственное нормативное описание его payload. Здесь не создаётся вторая версия. Модуль встроен в Go, внутренний интерфейс не является HTTP endpoint.

## 9. Границы реализации

Нет API регистрации, админки, черновиков, автосохранения, истории, загрузок в чат, автоматического чтения URL, AI-редактирования опубликованного материала. Подтверждение — действие интерфейса, сервер независимо проверяет сессию/владельца/тело; поле confirmed не способ защиты. Заглушка бота не заменяет проверки прав и не должна открывать публичный обход авторизации.
