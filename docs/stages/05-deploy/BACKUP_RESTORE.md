# Резервное копирование и восстановление

Скрипты создают согласованную копию PostgreSQL и тома изображений `media_data`. Они используют службы `db` и `api` из `compose.yaml`. На Linux нужны Docker Compose v2 с поддержкой `--wait`, POSIX shell, GNU tar, GNU coreutils, а также стандартные `cmp`, `grep`, `sed`. PostgreSQL и инструменты работы с томом запускаются в существующих образах проекта.

## Создание копии на сервере

В каталоге проекта выполните команду.

```sh
sh scripts/backup.sh
```

Архив появится в `backups/nir18-<дата-UTC>-<идентификатор>.tar.gz`. Последняя строка стандартного вывода содержит полный путь. Можно указать свой каталог.

```sh
sh scripts/backup.sh /srv/nir18-backups
```

На время снятия копии скрипт останавливает API с ожиданием завершения процесса. Вместе с ним прекращаются загрузки, изменения статей и очистка изображений. PostgreSQL продолжает работать. Во время этого окна веб-интерфейс может показывать ошибку недоступности API. По завершении, в том числе при ошибке создания копии, скрипт запускает ранее работавший API и ждёт его готовности. Если API был остановлен до запуска скрипта, он останется остановленным.

Для одного контейнера БД одновременно допускается одна операция обслуживания. Блокировка представлена остановленным служебным контейнером `nir18-backup-<id контейнера БД>`. При обычном завершении и обрабатываемых сигналах скрипт снимает блокировку. После аварийного завершения компьютера сначала убедитесь, что другие операции закончены, затем удалите только соответствующий служебный контейнер через `docker rm <имя>`.

Архив содержит следующие файлы.

| Файл | Содержимое |
| --- | --- |
| `database.dump` | Логическая копия БД через `pg_dump -Fc` |
| `media.tar` | Полный том изображений, включая промежуточные загрузки |
| `media-files.sha256` | Список и SHA-256 всех сохранённых файлов |
| `ready-files.sha256` | Ключи готовых изображений и SHA-256 из БД |
| `metadata.txt` | Дата UTC, commit кода, major-версия PostgreSQL, версия миграций, число файлов |
| `SHA256SUMS` | Контрольные суммы пяти файлов копии |

Скрипт проверяет готовые изображения по данным БД до создания архива. Итоговый файл появляется только после завершения упаковки. Каталог `backups/` исключён из Git. Копия содержит учётные данные приложения в виде записей БД, поэтому доступ к ней ограничивается. Перенесите готовый архив на отдельный хост или в защищённое хранилище с шифрованием, как предусмотрено архитектурой проекта. Настройки `.env` хранятся отдельно и должны быть подготовлены на целевом сервере.

## Восстановление в отдельный проект

Для восстановления используйте соответствующую архиву версию кода и ту же major-версию PostgreSQL. Commit и версию схемы можно прочитать из архива.

```sh
tar -xOf /srv/nir18-backups/nir18-<дата>-<идентификатор>.tar.gz metadata.txt
```

Подготовьте каталог проекта с `.env` и образами приложения. Для контрольного восстановления задайте отдельное имя проекта и свободный порт. Docker создаст для него собственные тома.

```sh
export COMPOSE_PROJECT_NAME=nir18-recovery
export WEB_PORT=8088
export APP_ORIGIN=http://localhost:8088
docker compose build
sh scripts/restore.sh /srv/nir18-backups/nir18-<дата>-<идентификатор>.tar.gz
docker compose up -d --wait
sh scripts/check-local.sh http://localhost:8088
```

Скрипт сам запускает только PostgreSQL. В целевом проекте API должен быть остановлен, БД и том `media_data` должны быть пустыми. Попытка восстановления поверх действующего сайта или существующих данных завершится ошибкой.

До записи данных проверяются состав архива, его контрольные суммы, пути файлов, версия формата и PostgreSQL. Восстановление SQL выполняется через `pg_restore --single-transaction --exit-on-error`. После загрузки файлов проверяются их полный список, число и SHA-256, а также соответствие готовых изображений записям БД. Для файлов устанавливается владелец `app`, используемый контейнером API.

После восстановления удаляются старые сессии и технические квитанции операций `mutation_receipts`. Участники входят заново с прежними паролями. API запускается отдельной командой после успешного завершения всех проверок. При ошибке восстановления он остаётся остановленным. Для повторной попытки после частичного восстановления подготовьте новый пустой проект. Сохраняйте единственную рабочую копию до окончания приёмки.

После запуска проверьте готовность API, тексты статей, загрузку изображений, вход владельца и запрет редактирования чужой публикации. Переключение домена на восстановленный экземпляр выполняется после этой проверки.

## Запуск из PowerShell

Для выполнения этих же shell-скриптов в Windows подходит Git Bash из Git for Windows. PowerShell должен находиться в папке проекта.

```powershell
& 'C:\Program Files\Git\bin\bash.exe' ./scripts/backup.sh
```

Для контрольного восстановления задайте отдельный проект, порт и адрес сайта. Укажите абсолютный путь к созданному архиву.

```powershell
$env:COMPOSE_PROJECT_NAME = 'nir18-recovery'
$env:WEB_PORT = '8088'
$env:APP_ORIGIN = 'http://localhost:8088'
docker compose build
& 'C:\Program Files\Git\bin\bash.exe' ./scripts/restore.sh 'C:/путь/к/архиву.tar.gz'
if ($LASTEXITCODE -ne 0) { throw 'Восстановление завершилось ошибкой' }
docker compose up -d --wait
```

После работы в этом окне очистите переменные, чтобы последующие команды снова обращались к обычному стенду.

```powershell
Remove-Item Env:COMPOSE_PROJECT_NAME, Env:WEB_PORT, Env:APP_ORIGIN
```

## Проверка сценария восстановления

Контрольный цикл выполняется на отдельном стенде. Создайте через API статью с загруженным рисунком и сохраните текст, адрес рисунка и SHA-256 исходного PNG. Выполните `backup.sh`, удалите контейнеры и оба тома только этого тестового проекта, затем восстановите архив через `restore.sh`.

После запуска сайта текст статьи и байты изображения должны совпадать с исходными. Старые сессии должны завершиться, прежние пароли должны позволять войти. Другой участник получает отказ при изменении чужой статьи. Дополнительно проверяются повреждённый архив, непустая цель, несовпадение версии PostgreSQL и отсутствие файла готового изображения.

Результаты выполненного цикла приведены в [отчёте проверки](BACKUP_RESTORE_TEST.md).
