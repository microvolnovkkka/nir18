| Этап | Учебные недели | Команда, чел.-ч | Из них разработчик сайта, ч |
| --- | --- | --- | --- |
| 1. Проектирование | Начало 9-й, 2–3 дня | 8–12 | 4–6 |
| 2. Проект, БД и API | 9–10 | 20–28 | 14–20 |
| 3. Публичные страницы и поиск | Вторая половина 10-й — 11-я | 16–22 | 12–16 |
| 4. Рабочий раздел и редактор | Вторая половина 11-й — 12-я | 16–22 | 12–16 |

| 7. Резерв и демонстрация | 15-я | 8–12 | 4–6 |

Оценки взяты из ТЗ: этапы 1–6 — **90–128 чел.-ч**, в том числе **60–84 ч** разработчика сайта; с резервом **98–140 / 64–90**. В ТЗ указана согласованная с PM средняя нагрузка разработчика сайта 10–14 часов в неделю. Дополнительные изображения и удаление публикаций требуют уточнения трудозатрат, прежде всего этапов 2, 4 и 6. Эти числа не пересчитаны автоматически.

Часы исследований и внутренняя реализация модуля бота в суммы сайта не включены. Пересечение календарных этапов не означает удвоение доступного времени одного разработчика.

**Готово, когда:** для каждого обязательного сценария понятно, какой экран/запрос/данные его реализуют; нет неразрешённых противоречий между сайтом и модулем бота. Не все внешние ресурсы обязаны уже существовать.

## Этап 2 / 2.3.2. Подготовка проекта, БД и серверного API

**Уточнение поручения 28.10.2026:** часть 1 — общий репозиторий, каркас React/Go, pgx, схема/сиды и миграции, Compose, техническая проверка и README. Часть 2 — служебная настройка паролей, вход/выход, права и базовый предметный API. Текущая работа останавливается после части 1. Полный список этапа ниже описывает обе части и не означает, что они уже реализованы. Факты — в DEVELOPMENT_STATUS.

**Ответственный:** разработчик сайта Маврин Ф. М. **Участники:** он же, тестировщик Воропаев А. К., разработчик бота Комаров А. С. — согласование интеграции.

**Зависимость:** данные и контракты этапа 1.

**Задачи:**

1. Создать структуру React/TypeScript/Vite, Go/net/http, PostgreSQL/pgx, SQL-миграции и локальный Docker Compose. Подготовить пример конфигурации без секретов и команду запуска.
2. Реализовать служебную инициализацию пяти аккаунтов, направлений и подтем; вход/выход и серверную проверку прав. Публичную регистрацию и административную панель не создавать.
3. Реализовать API чтения каталога/статей, поиска/фильтров, создания, ручного обновления и удаления своей статьи. Сервер назначает автора и время обновления. Публикации не имеют статуса черновика.
4. Реализовать приём multipart, проверку размера/формата/пикселей, уникальные имена, метаданные и выдачу изображений с проверкой доступа. Связывать файлы с публикацией, очищать только невостребованные загрузки по спроектированным правилам.
5. Подготовить интерфейс модуля бота и тестовую заглушку, не требующую API-ключа. Проверить ошибки запросов, владение статьями/изображениями и согласованность сохранения/удаления.

**Результат:** воспроизводимый локальный сервер с БД, миграциями, тестовыми данными и основным API. К началу этапа 3 доступно API чтения; оставшиеся серверные операции можно завершать параллельно в рамках доступных часов.

**Готово, когда:** повторяемо запускается по инструкции; чужую статью нельзя изменить/удалить прямым запросом; временные изображения закрыты; сохранение статьи/связей корректно, ошибки обрабатываются без частичного результата.

**Ответственный:** разработчик сайта Маврин Ф. М. **Участники:** он же, content manager Кондратьева Е. А., тестировщик Воропаев А. К.

**Зависимости:** права/API этапа 2, навигация и рендерер этапа 3.

**Задачи:**

1. Реализовать вход, список собственных материалов, создание новой статьи и открытие своей опубликованной статьи для ручного редактирования.
2. Создать общий Markdown-редактор: заголовок, направление/подтема, кнопки разметки, переход в предпросмотр. Нельзя присвоить себе другого автора.
3. Добавить загрузку изображения, вставку ссылки в выбранное место, описание, замену и удаление из Markdown; сохранять состояние при переключении вкладок и ошибке загрузки.
4. Реализовать явное подтверждение публикации/обновления, понятный успех/ошибку и защиту от случайных повторов. До успешного обновления читателям доступна прежняя опубликованная информация.

6. Проверить редактор на ПК/телефоне и отсутствие непредусмотренных серверных черновиков, автосохранения и версий.

**Результат:** полный ручной цикл создания, проверки, публикации, обновления и удаления; готовые общие компоненты для страницы бота.

**Готово, когда:** автор выполняет цикл целиком через сайт; после обновления меняются содержимое и «Обновлено», права соблюдены, файлы не теряются при ошибке, удалённая статья не выдаётся как существующая.

## Этап 5 / 2.3.5. Страница бота и подключение модуля

**Ответственные:** разработчик сайта Маврин Ф. М. — интерфейс и публикация; разработчик бота Комаров А. С. — модуль генерации. **Участники:** оба разработчика, тестировщик Воропаев А. К., content manager Кондратьева Е. А.

**Зависимости:** редактор и общий обработчик публикации этапа 4; контракт модуля этапа 1. Реальный модуль разрабатывается вторым разработчиком параллельно.

**Задачи сайта:**

1. Создать авторизованную страницу с чатом, Markdown-редактором и предпросмотром. Бот помогает только с новым отчётом.
2. Подключить тестовую заглушку по согласованному контракту; показать тестовый режим, ожидание, ошибку и повторную попытку.
3. Реализовать выбор ответа и «Сформировать черновик»: перенос выбранного результата без повторного запроса к модели и без записи отчёта в БД.
4. Реализовать предложенную замену через «Применить»; сохранять ручные правки до подтверждения и ссылки на вставленные изображения. Общий загрузчик работает в редакторе этой страницы; файлы модели не передаются.
5. Публиковать после явного подтверждения тем же обработчиком сайта. Переключение вкладок сохраняет текущее состояние; опубликованные статьи далее редактируются вручную.
6. После готовности модуля второго разработчика заменить заглушку, подключить конфигурацию и проверить полный сценарий с реальным API.

**Результат:** цепочка «текст → ответ → перенос → правки/изображения → предпросмотр → подтверждение → публикация» на ПК и телефоне.

**Готовность разделять:** интерфейс/контракт можно принять на заглушке; реальная интеграция считается проверенной только после подключения рабочего модуля и выполнения запросов к выбранному поставщику. В `DEVELOPMENT_STATUS.md` записывать оба результата отдельно.

Внутренняя генерация, промпт, поставщик и ограничения — ответственность разработчика бота. Без нового поручения не заменять это самостоятельной реализацией всего модуля в чате сайта.

## Этап 6 / 2.3.6. Размещение и итоговая проверка

**Ответственные:** разработчик сайта Маврин Ф. М. — размещение и исправления; тестировщик Воропаев А. К. — приёмка; content manager Кондратьева Е. А. — оформление материалов. **Участники:** все трое, разработчик бота Комаров А. С., PM Мушкетов Е. В.

**Зависимости:** основные функции предыдущих этапов; для публичного размещения нужны выбранные сервер и домен. Сейчас их нет — подготовку и проверки выполнять локально.

**Задачи:**

1. Подготовить конфигурацию Compose/Caddy, постоянные тома БД и изображений, маршруты API/медиа, настройки окружения и инструкции запуска. После появления сервера/домена настроить HTTPS.
2. Настроить совместное резервное копирование БД и файлов в отдельное место; проверить восстановление. Проверить сохранность после пересоздания контейнеров и очистку невостребованных загрузок.
3. Добавить реальные подготовленные материалы, проверить каталог/фильтры и отображение Markdown, формул, таблиц, кода и изображений.
4. Выполнить приёмочные сценарии ниже, исправить блокирующие ошибки, проверить реальные ошибки модели и мобильный интерфейс.
5. Подготовить краткую инструкцию команды: вход, публикация, изображения, обновление/удаление, работа бота, отсутствие восстановления несохранённой работы после закрытия страницы.

**Результат:** обязательные сценарии проверены; после появления инфраструктуры сайт доступен по согласованному адресу. Локальный стенд не обозначать как уже развёрнутый публичный сайт.

**Основные сценарии приёмки:**

- Читатель без входа находит статью поиском и сочетанием фильтров, открывает её на ПК/телефоне.
- Автор вручную создаёт отчёт с таблицей, кодом, формулой и изображением, подтверждает публикацию, обновляет и удаляет свою статью.
- Другой участник не может менять/удалять чужую статью; читатель не получает доступ к генерации и временным загрузкам.
- Загружаются PNG/JPEG/WebP в пределах лимитов. Неподдерживаемые/повреждённые файлы, превышение размера/пикселей, одинаковые исходные имена, обрыв связи и заполненный диск обрабатываются без потери редактора.
- Замена картинки показывает новый файл после сохранения; действующие ссылки не ломаются; публикация с изображениями восстанавливается из согласованной копии БД/файлов.
- Бот принимает текст, «Сформировать черновик» не вызывает новую генерацию, новый ответ не стирает правки без «Применить», изображения сохраняются, публикация происходит только после подтверждения.
- Ошибки сети/API и повторы не создают случайные дубли и не уничтожают открытый материал. Переключение вкладок не сохраняет черновик в БД.

## Организация работы

- Переходить к следующей задаче по готовности зависимостей; не требуется ждать полного окончания всех соседних работ, но нельзя опираться на отсутствующий API без согласованной заглушки.
- Тестировщик проверяет результат каждого этапа, а не только финальный продукт. Content manager параллельно готовит каталог, схемы экранов и примеры материалов; PM координирует сроки и ресурсы.
- В исходном плане рабочий модуль бота нужен к завершению 12-й недели для интеграции на 13-й. Реальные сроки согласуются по прогрессу и доступности API; они не следуют из текущей даты автоматически.
- Опциональные функции не входят в обязательные критерии завершения. Основной объём определяется требованиями, а не количеством оставшегося времени.
- После этапа обновлять `DEVELOPMENT_STATUS.md`: результат, файлы/коммит, проверки, оставшиеся вопросы и следующий шаг.
