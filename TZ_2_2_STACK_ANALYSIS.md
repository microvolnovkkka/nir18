# 2.2. Выбор решения, стек и архитектурные границы

**Актуально: 28 октября 2026 года.** Выбранный подход и инструменты уже приняты. Конкретная схема данных и контракты API теперь подготовлены в [docs/stages/01-design](docs/stages/README.md); контракт бота ожидает подтверждения Александром. Ниже сохранены исходные архитектурные границы, а не утверждение о готовности функций. Новые решения пользователя: `DECISIONS_AND_QUESTIONS.md`.

## 1. Выбор подхода

Сравнивались три способа: готовая CMS (например WordPress), собственный интерфейс поверх headless CMS (например Directus) и собственное веб-приложение с API. Критерии — скорость разработки, интеграция бота, удобство публикации и компетенции команды.

CMS быстрее даёт стандартный блог, но чат, Markdown и подтверждение публикации всё равно требуют адаптации. Headless CMS предоставляет управление данными и API при свободе фронтенда, но добавляет отдельную платформу, её права и правила расширения. Собственное приложение требует больше базового кода, зато позволяет совместно спроектировать публикации, редактор, изображения и модуль бота под нужный сценарий.

**Выбрано собственное веб-приложение с Go, React/TypeScript и PostgreSQL.** Фёдор изучал Go; знакомый язык, HTTP/JSON в стандартной библиотеке, явные типы и сборка серверного приложения подходят задачам проекта. Это не утверждение о гарантированном превосходстве Go по скорости разработки. ИИ помогает писать код, но не заменяет проверку и тестирование.

Подробный сравнительный текст для учебного отчёта сохранён в локальном архиве анализа `docs/archive/2026-10-28-before-handoff/TZ_2_2_STACK_ANALYSIS.md` (не публикуется). Устаревание CMS не используется как аргумент выбора.

## 2. Выбранный стек

| Компонент | Инструменты | Назначение |
| --- | --- | --- |
| Клиент | React + TypeScript + Vite | Каталог, формы, чат, редактор, предпросмотр; сборка клиентского приложения |
| Навигация и оформление | React Router + Tailwind CSS | Страницы и адаптивная светлая тема |
| Markdown | Текстовое поле; react-markdown, remark-gfm, remark-math, rehype-katex / KaTeX | Общий рендерер, таблицы, код и формулы; не WYSIWYG-редактор |
| Сервер | Go + net/http | API, авторизация и права, публикации, каталог, изображения, интерфейс модуля бота |
| Данные | PostgreSQL | Учётные записи, каталог, публикации, метаданные изображений и связи |
| Доступ к БД | pgx + SQL-миграции | Запросы и воспроизводимая структура БД; исполнитель миграций выбирается при настройке |
| Обмен | HTTP API в стиле REST; JSON и multipart/form-data | JSON для обычных запросов; multipart для загрузок; HTTPS при размещении |
| Бот | Встроенный модуль Go; позднее DeepSeek API | Сейчас заглушка; второй разработчик подключает конфигурируемого поставщика/модель |
| Файлы | Постоянный Docker-том, Go, PostgreSQL | Изображения на диске, метаданные и связи в БД; загрузка/выдача с контролем доступа |
| Запуск | Docker Compose + Caddy | Окружение, фронтенд, проксирование Go; HTTPS после появления сервера и домена |

Точные версии зависимостей проверить по официальной документации на этапе создания проекта и зафиксировать в файлах зависимостей. Не считать старое название модели или пример версии обязательным.

## 3. Состав приложения

```text
Браузер: React — каталог / рабочий раздел / чат / Markdown / предпросмотр
    │ JSON / multipart-form-data / запросы изображений
    ▼
Caddy — интерфейс и маршрутизация (HTTPS в размещённой версии)
    ▼
Go — вход и права │ каталог/публикации │ изображения │ модуль бота
    │                    │                 │               │
    └──────────────── PostgreSQL     постоянный том    заглушка сейчас
                                                      DeepSeek позже
```

Go — одно серверное приложение с логическими модулями. Caddy не выдаёт каталог загрузок напрямую в обход Go: для временных файлов нужна проверка владельца. Постоянно работающий отдельный Python-сервис, очередь задач, Redis, объектное хранилище, векторная БД и микросервисы не требуются согласованным объёмом.

Локальный режим должен запускаться без домена и API-ключа. HTTPS и реальный поставщик подключаются позднее. Локальная проверка не считается подтверждением готовности размещения.

## 4. Обязательные правила данных

- Автор публикации определяется по аутентифицированному аккаунту. Обновление/удаление — только автором, с серверной проверкой.
- Направления и начальные подтемы предварительно заносятся в БД, как и пять аккаунтов. Публичной регистрации и интерфейса управления этими справочниками нет.
- Подтема относится к одному направлению; API не должен сохранять противоречивую пару.
- Публикация содержит заголовок, Markdown, автора, подтему и время последнего успешного изменения. Источники могут находиться внутри Markdown.
- Подпись «Обновлено», фильтры и порядок «сначала новые» относятся к одному времени последнего обновления. Отдельная пользовательская дата первого размещения не требуется.
- Черновики и история диалогов не записываются в БД как материалы; нет таблицы версий публикаций. Технические сессии и метаданные временных файлов допустимы.
- Связи публикаций с изображениями должны отражать использованные внутренние ссылки. Сохранение статьи и обновление связей выполняются согласованно; ошибка не оставляет частично опубликованный материал.
- Удаление публикации снимает её связи; изображения, используемые другими публикациями, сохраняются. Физическая очистка не должна нарушать действующие ссылки.

### Что спроектировать, прежде чем писать миграции

Кандидаты сущностей: `users`, `directions`, `subtopics`, `publications`, `media`, связи публикаций/медиа и технические сессии. Это ориентир, а не утверждённый SQL. На этапе 1 определить идентификаторы, обязательные поля, индексы, связи, время, поиск и транзакции.

Механизм входа и служебного сброса пароля выбрать при проектировании; не добавлять публичные экраны регистрации/восстановления без нового требования. Пароли не хранить открытым текстом. Предусмотреть проверку прав, безопасную обработку Markdown и защиту изменяющих запросов в соответствии с выбранной схемой авторизации.

## 5. Изображения: приём, публикация и очистка

1. Автор нажимает «Добавить изображение» в общем редакторе.
2. **Авторизованный `POST /api/media`** принимает `multipart/form-data`. Проверяются размер файла/запроса, реальный формат, возможность прочитать изображение и число пикселей. PNG/JPEG/WebP, до 5 МиБ и 20 000 000 пикселей. Для проверки WebP предусмотрен `golang.org/x/image/webp`.
3. Go создаёт случайный идентификатор через `crypto/rand`, выбирает расширение по проверенному формату и сохраняет файл без перезаписи при совпадении. Оригинальное имя пользователя не определяет путь на сервере.
4. Файл помещается в постоянный том, например `media_data`, подключённый к Go в настраиваемый каталог. В БД сохраняются владелец, ключ файла, формат, размер/размеры изображения и техническое время загрузки. Имена тома и каталога — примеры.
5. API возвращает идентификатор/адрес, редактор вставляет `![описание](/media/<id>)`. До публикации Go разрешает просмотр временного файла владельцу. Сам URL не заменяет проверку доступа.
6. При подтверждённой публикации Go проверяет используемые внутренние ссылки и допустимость привязки, сохраняет статью и связи. После этого изображения доступны читателям.
7. При замене создаётся новый файл. Старый обслуживает прежнюю опубликованную информацию до успешного сохранения изменений. При удалении изображения из Markdown изменяется связь, а не немедленно уничтожается файл.
8. Очистка удаляет только невостребованные файлы после проверки отсутствия действующих связей. Срок жизни незавершённых загрузок и защита долгой открытой сессии редактирования определяются на этапе 1.

Состояние «не привязан к публикации» относится к файлу, а не к черновику отчёта. Метаданные временной загрузки не должны превращаться в скрытое сохранение Markdown.

Go обслуживает адрес `/media/<id>` с нужными правами; Caddy проксирует. Пересоздание контейнера не должно удалять постоянные данные. Предусмотреть согласованные резервные копии БД и файлов в отдельное место и проверку восстановления. Конкретные место и расписание ещё не выбраны.

Резервное восстановление данных сайта — эксплуатационная мера; оно не вводит интерфейс истории версий или корзину публикаций.

## 6. Граница API сайта и бота

**Зафиксировано:** общий сервер Go, генерация отдельно от публикации, API-ключ на сервере, `POST /api/media` для изображений. Детальные URL остальных операций и JSON-схемы утверждаются разработчиками на этапе 1.

В контракте нужны операции:

- вход, выход и получение текущего участника;
- чтение направлений/подтем, поиск и фильтрация публикаций, получение статьи;
- создание после подтверждения, ручное обновление и подтверждённое удаление своей статьи;
- загрузка изображения и выдача файла;
- запрос ответа бота по тексту/контексту текущего диалога, возвращающий результат или понятную ошибку.

«Сформировать черновик» не является серверной операцией: выбранный ответ переносится во фронтенде, нового вызова LLM нет. Бот не обновляет опубликованные статьи. Подробности нового отчёта и «Применить» — в `BOT_WORKFLOW.md`.

Фронтенд обращается к согласованному интерфейсу. На старте за ним заглушка, позже реальный модуль второго разработчика. Подмена не должна требовать переписывать публикацию/редактор. Конкретный endpoint поставщика, модель, ключ, тайм-ауты и лимиты задаются конфигурацией; реальные значения появятся позже.

## 7. Решения этапа проектирования, ещё не готовая архитектура

До реализации зафиксировать:

- маршруты экранов, состояния загрузки/ошибки/успеха и формы подтверждения;
- схему данных, транзакции публикации/удаления и индексы;
- авторизацию, сроки сессий, служебную инициализацию аккаунтов;
- API-контракты с примерами, лимитами и обработкой повторных запросов;
- поиск на русском и технических терминах, пагинацию, границы диапазонов дат;
- очистку изображений и согласованные резервные копии;
- сохранение ручных вставок при новом результате бота;
- команды локального запуска, тестовые данные и границу ответственности двух разработчиков.

Разумные технические решения можно принимать без нового продуктового опроса, документируя их основания. Не считать уже написанными миграции или обработчики только потому, что их обязанности перечислены здесь.
